## 2. Архітектура
```
bot/bot.py            Telegram-бот (python-telegram-bot 21.6). Лише інтерфейс: кнопки, питання, файли.
dispatcher/           boards.json — список сайтів; dispatcher.py — запускає програму сайту окремим
                      процесом, пересилає питання/відповіді, таймаут (час на відповідь не рахується),
                      журнал journal.jsonl.
boards/domria/        програма dom.ria (post_domria.py, mapping.py, domria_client.py, run.py)
boards/rieltor/       програма rieltor.ua (crm_to_rieltor_payload.py, rieltor_geo/photos/refresh_dates.py,
                      set_pickup_rate.py, run.py)
boards/olx/           програма OLX (olx_client.py, mapping.py, run.py)
boards/presentation/  інструмент «Презентація з OLX» (не сайт для публікації; "kind": "tool" у boards.json, розділ 8а)
crm/extract_estate.py парсер презентації CRM (спільний)
common/board_protocol.py  протокол між диспетчером і програмами сайтів
deploy/               cloud-init.yaml, install.sh, update.sh, realty-bot.service,
                      add-instance.sh / remove-instance.sh (слоти для інших людей, розділ 3)
extension/            розширення Chrome (не на сервері, ставляться в браузер): olx-cookies — вхід OLX для бота;
                      olx-presentation — презентація для клієнта з оголошення OLX (розділ 8а)
```
**Протокол** (stdout/stdin, JSON по рядку):
`{"type":"info","text"}` · `{"type":"ask","id","text","options":[…]|null,"allow_text","secret"?,"preview"?}` ·
`{"type":"result","ok","text","url","id","draft", …додаткові поля}`; відповідь на ask:
`{"id","choice":i}` / `{"id","text"}` / `{"id"}` (пропуск). У програмах: `bp.info`, `bp.ask_choice`,
`bp.ask_text`, `bp.result`. print() автоматично стає info. З консолі (tty) питання йдуть через input().
`preview` (10.11.2026) — довгий текст, який бот показує окремими звичайними повідомленнями перед питанням (ділить по ~4000
символів), напр. поточний опис, щоб скопіювати й виправити: `bp.ask_choice(..., preview=текст)`. Довга текстова відповідь:
Telegram ділить повідомлення > 4096 символів на кілька — бот (`collect_long_answer`) збирає частини (відповідь ≥ 3900
символів → чекає 2,5 с тиші) і віддає програмі одним текстом (частини через «\n»).
`editor` (10.11.2026) — `bp.ask_choice(..., preview=текст, editor="Заголовок")`: якщо на сервері є редактор, бот замість
preview дає кнопку «✏️ Відкрити редактор» (Telegram Mini App: поле з уже вставленим текстом, «Зберегти») — відповідь
приходить як звичайна {"text"}. Редактора нема — preview повідомленням, як раніше. Деталі — розділ 8а.
info збирається блоками (до 25 рядків), але відправляється не пізніше ніж за 2 с (таймер) — у чаті видно хід
роботи, навіть коли програма далі довго чекає на сайт (до 30.10.2026 рядки чекали 25 штук і губились при зависанні).
**Таймаут програми** (boards.json `timeout_min`, 25 хв): перед зупинкою диспетчер шле SIGUSR1 → програма пише стек
(faulthandler) у `logs/<сайт>.stderr.log`, а в чат іде «Зависла на: чекала відповіді сайту ← файл:рядок функція».

Кожна програма сайту розуміє: `post --url <CRM> [--techpassport файли…]`, `check`,
(rieltor ще `refresh`, `post --no-ask`; dom.ria ще `techpassport --realty-id N файли…`;
OLX ще `post --dry-run`).

## 3. Сервер
- Oracle Cloud Free Tier, VM «realty-bot», Ubuntu 24.04, E2.1.Micro (x86), створена через
  cloud-init (deploy/cloud-init.yaml → install.sh: swap, apt, git clone, venv, systemd).
- Код: `/opt/realty-bot`, venv `.venv`. Дані: `/var/lib/realty-bot` (secrets/, logs/, journal.jsonl,
  domria/, rieltor/, olx/ — звіти й логи запитів). Налаштування: `/etc/realty-bot.env`
  (TELEGRAM_TOKEN, REALTY_DATA_DIR). Сервіс systemd `realty-bot`.
- У Claude немає SSH на сервер. Оновлення — команда `/update` у боті. Логи — `/logs`.
- Стара VM (instance-20260915-1204) ще існує — видалити лише після мого «так».
- **Слоти для інших людей** (30.10.2026): на тій самій VM можна запускати окремі копії бота для інших
  людей — свій Telegram-бот, код `/opt/realty-bot-<ім'я>` (свій venv, свій `/update`), дані
  `/var/lib/realty-bot-<ім'я>`, налаштування `/etc/realty-bot-<ім'я>.env` (TELEGRAM_TOKEN, REALTY_DATA_DIR,
  `REALTY_INSTANCE=<ім'я>`, опційно OWNER_ID), сервіс `realty-bot-<ім'я>`. Код бота й програм сайтів від цього
  не залежить (усе через REALTY_DATA_DIR і власну теку), тож мій бот і мої дані не зачіпаються.
  Створення/видалення — `deploy/add-instance.sh <ім'я>` / `remove-instance.sh <ім'я> [--purge]` (root), або
  з мого бота: `/newbot`, `/bots`, `/delbot` (бот запускає скрипти через `sudo -n`; ці команди є лише в головному
  боті, де REALTY_INSTANCE порожній). add-instance перевіряє токен через getMe, не дає один бот у двох слотах,
  при збої прибирає створене; remove лишає дані слота (без --purge). Пам'ять VM спільна (1 ГБ + swap).
  ⚠️ На реальному сервері ще не запускалось (перевірено в пісочниці з імітацією systemd і Telegram).

## 4. Бот: меню і сценарії
Кнопки (з 10.11.2026): 📤 Викласти оголошення · 🔑 Вхід · 📄 Презентація (до 10.11 — «Презентація з OLX», стара назва теж працює) · 🔄 Оновити дати rieltor · 🗑 Видалити оголошення rieltor (лише головний бот).
Прибрано 10.11.2026: «📎 Техпаспорт до чернетки» (код сценарію лишився, вхід до нього вимкнено) і «ℹ️ Статус» (лишилась команда /status);
«🔑 Вхід» перейменовано на «🔑 Вхід».
/cancel зупиняє програму сайту, що працює зараз (kill процесу, dispatcher.cancel_all), і не запускає наступні сайти; пакет rieltor зупиняється одразу.
Команди: /start (перший — стає власником), /cancel, /update, /logs, /status, /id;
лише в головному боті — /newbot, /bots, /delbot (слоти, розділ 3).

**Викласти оголошення:** спершу вибір сайтів →
- лише rieltor: можна одне посилання, кілька (кома/рядки) або .txt → **пакет**: у фоні по черзі
  (пауза 5 с), без питань (`--no-ask`), у чаті тримаються звіти лише поточного й попереднього
  оголошення, решта видаляється; наприкінці один підсумок (✅/❌ по артикулах). /cancel зупиняє одразу
  (поточне оголошення обривається). Пакет сам зупиняється при протухлих cookie або ліміті фото rieltor (`stop_batch`).
- інші сайти: одне посилання → зведення → (для dom.ria техпаспорт: PDF / кілька фото / нічого)
  → підтвердження → публікація.
Просто кинуте посилання — зведення, потім вибір сайтів. Кинуте посилання на оголошення OLX або dom.ria — одразу презентація (нижче).

**Презентація з OLX / dom.ria** (10.11.2026): кнопка → посилання на оголошення OLX або dom.ria (`realty-…-<ID>.html`, будь-яка мова) → бот питає підпис (один раз, далі — зі збереженого)
і показує зведення з кнопками «✅ Зробити / 💲 Змінити ціну / 🚫 Без ціни / 📝 Змінити опис / ✍️ Змінити підпис» → посилання Telegraph + PDF документом.
«📝 Змінити опис» (10.11.2026): кнопка «✏️ Відкрити редактор» (Mini App з поточним текстом; якщо редактора нема —
поточний опис окремим повідомленням, `preview`, щоб скопіювати) → новий текст повністю замінює
опис (контакти з нього НЕ вирізаються — це текст ріелтора); кнопки «↩️ Як на OLX» і «🗑 Без опису». У зведенні — «Опис: N симв.
— ваш текст («перший рядок…»)».
Деталі — розділ 8а. Програма повертає файли полем `files: [{"path","name"}]` у result — бот (`send_result_files`) надсилає їх
документами, лише з теки даних бота. Інструменти в boards.json мають `"kind": "tool"`: `D.boards()` їх не віддає
(вибір сайтів, «Вхід», /status), `D.boards(enabled_only=False)` — віддає (запуск).

**Вхід (раніше «Cookies»):** вибір сайту → повідомлення з cookie (або для OLX — рядок Authorization) → бот зберігає
у `secrets/<сайт>_cookies.txt` / `<сайт>_auth.txt` (chmod 600), видаляє повідомлення, запускає `check`.
Є ще окремий пункт «CRM (адмінка…)» — не сайт-«дошка», `check` не запускається, лише зберігає
`secrets/crm_admin_cookie.txt` (для звірки категорії при постингу землі на rieltor, розділ 7).

  11 офіс, 12 офісна будівля, 14–22 комерція, 25–27 ділянки, 31–35 гаражі.
- realty_sale_type = 1 завжди. Стіни: WALL_ALIASES (газоблок↔газобетон), дефолт цегла.

## 7. rieltor.ua
- Cookie. `POST /api/offers/`; фото `/api/offers/upload-photo/` (мін. ширина 1200 — дрібні
  розтягуються; мін. 3 фото — дублюється останнє; ліміт `image_upload_rate_limit` → чекати 5 хв, до 3 разів = 15 хв, далі `RateLimitExhausted` → пакет зупиняється
  з поясненням; сума очікувань має бути < таймауту диспетчера 25 хв — раніше було 12×5 хв, і замість «ліміт фото»
  диспетчер мовчки вбивав програму: «працювала задовго». Ліміт — на акаунт (30.10.2026: після ~200 оголошень за день
  мій акаунт гальмував/зависав, а акаунт колеги з того ж сервера викладав швидко). Вантажити порціями, не 200 за день).
- Продаж будинку вимагає groundArea (питаємо або в пакеті пропускаємо).
- **Визначення типу з заголовка CRM** (`parse_deal_title`): ріжемо лише по ПЕРШОМУ «/» (сама
  назва типу іноді теж містить слеш, напр. «С/г ділянка»). Якщо точного рядка нема в
  `ITEM_TYPE_BY_DEAL` — запасний варіант за ключовим словом (`ITEM_TYPE_KEYWORDS`, земля/ділянка —
  найвищий пріоритет), інакше мовчки падало в дефолт «Комерційна» (була реальна помилка на
  «Земля під інд. будівництво» → публікація як комерція → renta_address_invalid, 22.10.2026).
- **Продаж ділянки (itemType=5):** rieltor.ua приймає поле `cadastralNumber` (рядок, формат
  `3220882200:03:005:1306` — підтверджено реальним HAR). Шукаємо його регуляркою
  `\d{10}:\d{2}:\d{3}:\d{4}` у вільному тексті опису CRM (`find_cadastral_in_text()` у
  `crm_to_rieltor_payload.py`) і кладемо в payload. Якщо в описі кадастру нема — об'єкт
  пропускається одразу (без фото/публікації, без питань навіть поза `--no-ask`), щоб можна
  було вантажити всю землю з CRM без ручної перевірки кожного оголошення (22.10.2026).
- **Звірка категорії через CRM-адмінку (новий, окремий `crm/extract_estate_admin.py`):**
  заголовок CRM (deal_title) заповнюється автоматично, але рієлтори іноді редагують його
  вручну і ламають розпізнавання типу. На авторизованій сторінці об'єкта
  (`crm-capital.realtsoft.net/estate/<id>`, НЕ публічна презентація) є таблиця «Характеристики»
  з полями «Категорія» (Житлова/Комерційна/Земельні ділянки) і «Тип» — підтверджено на
  реальній сторінці користувача. Якщо в `secrets/crm_admin_cookie.txt` є cookie CRM-сесії
  (кнопка бота «🔑 Вхід» → «CRM (адмінка…)», окремо від rieltor/dom.ria/OLX cookie) —
  `check_land_category()` у `boards/rieltor/run.py` перед постингом звіряє категорію; якщо
  вона «Земельні ділянки» — примусово `itemType=5` (`item_type_override` у `build_payload`),
  незалежно від заголовка. Best-effort: без cookie або при помилці запиту — мовчки fallback
  на визначення з заголовка, нічого не блокує (22.10.2026).
- **Квартири (itemType=1), продаж** (22–25.10.2026; за реальним HAR створення квартири в ЖК «Либідь»):
  `fill_flat()` у `crm_to_rieltor_payload.py`. Поля payload: `roomCnt, floor, floorCnt` (рядки), `commonState`,
  `commonArea/usefulArea/kitchenArea`, опис `description1`, фото `rentaImages1`; з даних rieltor.ua про
  будинок (ЖК/будинок знайдено) додаються `wallType, houseProjectType, detailParams{year,ceilHeight}`.
  Джерела по черзі: CRM-параметри → дані rieltor про будинок → текст опису («24 поверх», «3 кімнати»,
  «5 з 9») → для житлової/кухні 40%/20% від загальної (окремо для кожної). Ставка — мінімальна для категорії
  (179 для квартир, `fetch_min_rate`). Що не визначилось — бот питає (`resolve_missing_flat` у `run.py`);
  у пакеті (`--no-ask`) квартира пропускається з переліком, чого бракує. Адреса: є ЖК у CRM → усе з даних
  rieltor (ЖК → вулиця → будинок); нема — вулиця+район; якщо вулиці нема в районі з CRM — перебираємо інші
  райони міста (`fix_district`, лише квартири): один збіг → беремо його, кілька/жодного → питаємо.
  ⚠️ Не перевірено на живому постингу: чи обов'язкові `wallType/houseProjectType/year/ceilHeight` для
  квартир, і `ptolemyHouseId` (лишаємо None, як у будинках).
- **Перевірка площ квартири** (26.10.2026): rieltor.ua відхиляє, якщо загальна < житлова + кухня
  («Загальна площа не може бути менше суми інших площ»). Якщо за даними CRM сума більша — бот просить ввести

## 9. Корисні уроки
- Chrome «sanitized» HAR вирізає cookie, Authorization і тіла відповідей — достатньо для структури запитів.
- Не брати координати з CRM (бувають неправильні). Регулярки на адресу — лише з межами слів
  («ЖК» ловило «Стежки»).
- Завжди перевіряти відповідь сайту по суті (status у тілі), а не лише HTTP 200.
- Тестувати категорії чернетками; реальні публікації — лише з дозволу.
- **dom.ria записує оголошення на `user_id` з payload, а не на власника cookie** (04.11.2026: зі слота колеги
  оголошення падали на мій акаунт — у коді був зашитий мій user_id за замовчуванням). Тепер user_id береться
  з `$REALTY_DATA_DIR/domria/config.json`: run.py шукає його у відповіді /v1/api/user/balance (якщо там є),
  інакше питає один раз у боті; якщо ID із сесії ≠ збереженому — зупиняється. Зашивати ID акаунтів НЕ можна.
- rieltor.ua за Cloudflare (з 30.10.2026): блокує діапазони IP GitHub Actions — Error 1008 «The site owner has blocked
  your IP address» (ip_range), HTTP 403 незалежно від cookie; монітор site-monitor2 з GitHub через це падає (його
  повідомлення «протух SITE_COOKIE» вводить в оману). З Oracle-сервера rieltor пускає. Перевірка — ручний workflow
  «Діагностика доступу» в site-monitor2. Того ж дня — ліміт завантаження фото на акаунт («Перевищено ліміт
  завантаження фото. Спробуйте пізніше», і в браузері теж) після ~200 оголошень; наступного дня знявся.
  02.11.2026: site-monitor2 як проміжний варіант перевіряє лише продаж квартир (1,1) і будинків (3,1) —
  `MONITORED_CATEGORIES`; решта вимкнена (не видалена). Список береться фільтром сайту: `/api/offers/list/` приймає

### Глобальна ідея: система керування рекламою на rieltor.ua (концепт, 29.10.2026 — займусь пізніше)
- Оголошення викладаються на rieltor (автоматично або мною) і висять там.
- По кожному збирається статистика: як активно дивляться (перегляди, відкриття телефону — див. п. 2)
  + заявки, які я вношу вручну.
- На основі цього система ділить оголошення на ті, що варто платно рекламувати, і ті, що ні —
  платне розміщення на rieltor дороге, гроші не мають іти на «мертві» оголошення.
- Плюс rieltor: оголошення можна міняти щодня, тож у рекламі мають лишатися лише найцікавіші.
- Монітор ЛУН (окремий проєкт: стежить, щоб платні оголошення були «представником» на lun.ua,
  піднімає ставку) тримає рекламовані в топі.
- Будівельні блоки: п. 1 (таблиця об'єктів), п. 2 (статистика), п. 3 (вибір ціни/ставки), монітор ЛУН.
